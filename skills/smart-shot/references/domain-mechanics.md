# Domain mechanics

Compile domains from each intent's context, lifecycle, stakes, dependencies, and
acceptance needs; never start from a fixed roster.

## Domain Brief

Discover what a real practitioner must decide and verify. For every retained concern
record: domain/subdomain and decision relevance; prompt/context evidence versus
assumption or missing evidence; mechanisms, states, invariants, methods, standards,
and measurements; generalist trap, edge/failure cases, and lifecycle consequence;
authority/source class with freshness or jurisdiction needs; affected decision,
check, dependency, and failure severity.

Run one uniqueness sweep for domain-specific concerns missed by universal axes.
Retain a concern only if it can change a decision, test, dependency, risk, or artifact.

## Materiality and specialist topology

Keep one ledger. Mark each material concern `ACTIVE` when it changes current work,
`CONDITIONAL(trigger)` when a named observation activates work, or `UNRESOLVED` when
routing needs evidence. Record owner and verification effect. Status never licenses
token-budget pruning; safety, legal, irreversible, or catastrophic concerns cannot
be demoted for plan size.

Derive specialists from the ledger. Split for materially different competence,
authority, evidence regime, professional artifact, or independent validation duty;
merge only when one qualified practitioner can own adjacent concerns without hiding
conflicts or weakening checks. Every concern maps to an owner and acceptance effect;
every specialist maps to a concern. Put conditional concerns, triggers, and actions
in the relevant charter.

Encode true execution dependencies as an acyclic graph: a dependency requires a
named upstream artifact before an expert can begin or finish. Put consultation and
reconciliation in interfaces/conflicts, not opposing edges. Repair cycles before
dispatch. Keep the Domain Brief available to execution and verification, and
recompile affected charters when a condition fires or routing resolves.
