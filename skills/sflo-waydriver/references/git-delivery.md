# Git delivery

Derive the delivery endpoint from the person’s requested result and standing project agreement. A request whose result requires remote availability authorizes that publication within its evidenced repository, audience and branch boundaries, even without the word “push”. Record that basis in the work record and carry it through handoffs. Tool access and reviewer approval establish different facts: acceptance proves readiness; the person’s request or agreement supplies publication authority.

Establish readiness from the current candidate-bound acceptance reports and required checks. Reconcile any conflicting completion claim with those observed results before publishing; incomplete acceptance stays pending while its missing evidence is obtained.

When publication is within that authority, push each independently accepted coherent increment to the agreed branch. Merge, release and deployment follow their own agreed endpoints. Read-only investigation finishes with its requested findings; local-only work remains local.

Inspect the complete outgoing changes, including pre-existing commits, against the authorized scope and project branch policy. Keep unrelated work outside that publication. Complete the required commit, push or pull request to the bound repository, remote and branch.

Verify the remote ref against the intended commit; for a pull-request endpoint, verify its base and head and return its link. Record that published identity in the existing work record. Reuse valid acceptance evidence and conclude once publication is verified. An unresolved acceptance finding, uncertain publication boundary or missing required check keeps publication pending: state the exact gap, pursue available evidence, and ask for the person’s decision or help when it controls progress. Apply the conductor’s authority-and-blocker handoff for blocked delivery.
